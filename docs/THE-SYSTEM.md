# THE-SYSTEM.md — what was actually built, and why it took longer than four hours

The brief asked for one landing page in three or four hours. That page is done and tagged
(`git checkout timebox`). This file is about everything after the tag, because it is a different
kind of answer to a different question.

## The question the exercise is really asking

First Day has **60 landing pages**, 18 of them variants of the same funnel, cloned by hand. The
job posting is for **one engineer** who will own the whole rebuild. So the interesting question
was never "can this person rebuild a page" — it is:

> When one engineer owns 60 pages, what has to exist so that shipping the 19th variant costs
> almost nothing, and so nothing quietly breaks while nobody is looking?

Rebuilding the page answers the first half of a much smaller question. The rest of this repo
answers the real one.

## The four pieces, and what each one removes

### 1. The page is data, not code

Eleven generic sections with full schemas. All copy lives in section settings, product
metafields or metaobjects — the three places Shopify already makes editable and translatable.
Two more funnels (`kde`, `toddlers`) run off the same sections, generated by a one-line override
each, with their own product facts pulled from their own metafields.

**Removes:** the developer from the path of every new variant, every copy fix, and every
translation.

### 2. The estate is measured, not guessed

`tools/audit_lp_estate.py` fetches every `-lp` page in their sitemap and records what it is made
of: weight, section inventory, sections that render nothing, third-party load, build type, and
how much each page shares with the funnel already rebuilt. It emits a **backlog per page**, where
every item carries the measured number that justifies it.

**Removes:** the argument about what to migrate first. The sequence falls out of the data, and
the one input the file can't supply — traffic and revenue per page — is named explicitly as the
thing that should reorder it.

### 3. The work is a queue, not a wish list

`docs/receipts/estate.html` renders that data as a graph: one node per landing page, edges
between pages of the same funnel, and each node carrying its backlog with impact, effort, and
the agent that would do it. The items are shaped for an agent to pick up, not for a human to
re-derive.

**Removes:** the gap between "we know the site has problems" and "someone is working on one".

### 4. The standard survives the person

Every gate that protected this build now runs in CI on every pull request: schema validity, the
copy-fidelity gate that catches invented content, templates matching their generator, and a
performance budget. Each PR also gets its own preview theme, so a CRO manager reviews the change
in a browser before it merges.

**Removes:** the dependency on one person remembering to check. A gate only a human runs is not
a gate.

And `tools/section_loop.py` — analyst writes acceptance tests, a different model builds against
them, a browser decides, the first model reviews the diff — is the loop that produced the work,
kept in the repo so it can produce the next one.

## What this is not

It is not a claim that AI multiplies a team by 100. That framing is wrong and the people running
this business already know it: the bottleneck was never typing speed. It is that **the cost of a
change should not scale with the number of pages**, and that a small team can only move fast if
the guardrails are automatic rather than remembered.

The measurable version of the claim, on the one funnel that exists to test it:

| | Before | After |
|---|---|---|
| Lighthouse performance (mobile) | 26 | 73 |
| Total blocking time | 20,860 ms | 570 ms |
| Sections to maintain for this funnel | 19 | 11, two of them reused |
| Cost of the next variant | a cloned page | a template file and content entries |
| What catches a regression | a person looking | CI, on every PR |

## The honest accounting

This is more than four hours of work. It is separable — the tag marks where the brief's ask
ends — and it was a deliberate choice, not a scoping failure. The debrief is a conversation
about how the work gets done, so the most useful thing to bring was the machine that does it,
running, on their own data.

Everything here is native Shopify: Liquid, sections, metafields, metaobjects, selling plans, the
Section Rendering API, the GitHub integration. No framework, no headless, no vendor added. The
next engineer to open this repo needs to know Shopify, not to learn my stack.
